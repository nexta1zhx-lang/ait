# 持久化分析（手动加入 → 每 15 分钟问一次 AI → 最长 8 小时）

> 用户 2026-10-15 定的：「**在 k 线界面顶部加入持久化分析的图标，点击图标弹窗确定要加入持久化分析，
> 每隔 15 分钟分析一次，最长不超过 8 小时**」+「结论变化时站内提示 + 同时往 Telegram 发一条」。
>
> 起因：先想过「异动筛选表」（1h 单根 ≥5% + 后 2 根 15m 守住低点），拿 12 天真实 K 线回放之后
> 发现那条规则**确认通过率 96%（形同虚设）、裸用没有正期望**（6h −0.4%、24h −2.4%，
> 只有"量比 ≥5 + 破前高"这一小撮勉强持平）——用户判断"怎么设计都不太好"，改成**手动指定**：
> 他觉得哪个币值得盯，就让 AI 盯 8 小时。这一条把"选币"这件事交回给人，机器只负责**按时问、记住答**。

---

## 1. 规模（先算清楚，再谈设计）

| | |
|---|---|
| 频率 | 15 分钟一次，**对齐 15m 收线 + 20 秒**（`:00/:15/:30/:45`） |
| 上限 | 8 小时 ⇒ **最多 32 次** |
| 花费 | ≈ ¥0.007~0.02/次（deepseek-flash）⇒ **一个会话 ¥0.2~0.6** |
| 上游权重 | 0（走本地库 K 线 + 一次模型调用） |
| 同时 | 一个用户最多 **3 个**会话 |

瓶颈不是钱，是**「32 条结论怎么消化」**——所以核心不是"多问几次"，而是**结论时间线**。

---

## 2. 调度：一个 ticker + 库里的 `next_at`

```
server.ts 启动时起一个对齐到 15m 收线（+20 秒）的定时器
  → analysis/persist.ts 的 runPersistTick()
      ① expireSessions()：满 8 小时的先收掉
      ② dueSessions()：取 next_at <= now() 的（逐个跑，不并发）
      ③ 每个会话：runAnalysis({source:'persist'}) → 记结果 → next_at = 下一根 15m + 20 秒
      ④ 结论**跨档变化**才发通知（观望 → 可做 / 可做 → 不可做）
```

**为什么不是每个会话一个 `setInterval`**：

- 状态在库里 ⇒ **进程重启接着跑**，`next_at <= now()` 才算该跑；
- **错过的轮次不补**：补跑等于一次烧好几发，而且"那一刻"的行情已经过去了；
- 对齐收线 + 20 秒 ⇒ 每一轮喂进去的都是**刚收线**的那根，同一会话各轮口径一致、可横向比
 （20 秒是留给 K 线底座的落库时间）；
- 上一轮慢/失败不会把后面的挤乱（每轮自己算下一跳）。

`next_at` 的算法只有一处（`db/persist.ts` 的 `nextRunAt()`）+ 一个 ticker（`server.ts` 的
`persistLoop()`），**别在别处再算一份**。

---

## 3. 冻结口径（同一会话才是同一把尺子）

加入时把 `symbol / timeframe / days` 写死在会话里，之后页面上换周期**不影响它**。
否则同一个会话里前几条按 1h 问、后几条按 15m 问，32 条结论没法横向比。

**不把上一轮结论喂回提示词**：「上次你说能做」会把它锚住，32 条就退化成 1 条重复 32 遍。
（想"跟踪同一判断"是另一种玩法，别混进来。）

## 4. 数据

| 表 | 用途 |
|---|---|
| `persist_sessions` | 会话：谁盯哪个币、冻结口径、`started_at/ends_at/next_at`、`runs/failed`、`status/ended_reason`、最近一条结论（`last_verdict/last_line/last_price/last_at`） |
| `analyses`（既有表 + `source` 列） | 每轮的结论**照旧落这儿**（含当时价格），`source='persist'` 跟手动跑的分开；时间线就是按会话时间窗查它 |

⚠️ 唯一索引 `(user_id, symbol) WHERE status = 'active'` ⇒ 同一个币重复点不会开两条。
⚠️ 时间线**不另建映射表**：结论已经在 `analyses` 里了，再复制一份就是两边会不同步。

## 5. 通知（用户 2026-10-15 选的那条）

- ★ **只在"转成可做"那一刻**提醒（用户 2026-10-15：「只有可做才弹窗和发送 telegram」）：
  `观望/不可做 → 可做`，**第一轮就是可做也提醒**。`可做 → 走弱` 和 `不可做 ↔ 观望` 都不推
  —— 32 条里通常只有几条有意义，每条都弹就是噪音。判据 `enteredGo()`（前后端各一份，必须一致）。
- **站内**：页面开着时 30 秒轮询一次列表，跨档弹一条 toast（`frontend/src/persist.ts`）。
- **App 推送**（2026-10-15 用户：「加入 app 推送」）：`backend/src/notify/push.ts` 走 **FCM HTTP v1**，
  发给这个用户在 `push_tokens` 表里的**每一台设备**（App 启动时上报 token，见 `frontend/src/push.ts`）。
  点通知会跳到那个币的 K 线（`data.symbol`）。⚠️ **需要三样东西**（见 [MOBILE.md](./MOBILE.md)）：
  Firebase 项目 + `android/app/google-services.json`（打包用）+ 服务账号私钥（服务端发信用，
  `FCM_SERVICE_ACCOUNT_FILE=/opt/crypto-advisor/firebase-sa.json`）。没配就只打一行日志。
- **Telegram**：`backend/src/notify/telegram.ts`，复用服务器上现成的
  `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID`（原来只给部署脚本和看门狗用）。
  ⚠️ 消息里**只发一行摘要**（`excerptOf` 160 字）—— 模型给的是**一整篇 Markdown**，
  15 分钟一篇会把 Telegram 刷屏。
- 通知**永远不影响主流程**：没配 / 网络不通 / Telegram 报错 —— 只打一行日志。

### 档位判据（一处定义、两处实现，必须一致）

`backend/src/analysis/verdict.ts` 的 `verdictOf()` ↔ `frontend/src/markdown.ts` 的
`verdictKind()`：**抹掉 Markdown 记号 → 全文找 → 取最早出现的那一类**。

★ 实测修正（2026-10-15）：原来只看**前 260 字**，假设"结论一定在最前面"。可实际回答是
一整篇 Markdown（`# NIL/USDT 1h 判断` + `## 一、…`），档位那两个字在后面 ⇒ 明明"不可做"
却被判成"观望"。现在全文找，「不能做」比它内部包含的「能做」出现得更早，否定不会被误读。

## 6. 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/persist` | 会话列表（每个会话带**结论时间线**）+ 上限 |
| POST | `/api/persist` | 加入（body: `symbol / market / timeframe / days`） |
| DELETE | `/api/persist?id=` | 停止 |
| POST | `/api/persist/run?id=` | **立刻跑一轮**（等结果；平时是后台自己跑） |

时间线里每条带 **+1h / +4h 的涨跌**（拿 `analyses.price` 跟之后第一根 1h 收盘比）——
**这一列才是"这套值不值得继续开"的唯一判据**，别删。

## 7. 界面

- **入口**：K 线页顶部那一排动作里的**循环箭头**（挨着「测试」「配置」），
  亮着（蓝）= 这个币正在被盯。点一下开弹层。
- **还没加入** ⇒ 就是那句确认：每 15 分钟一次 / 最长 8 小时 / ≈32 次 ≈ ¥0.2~0.6 + 周期/天数选择。
- **已经在跑** ⇒ 第几次 · 下一次几点 · 还剩多久 · 最近那句；两颗按钮（立即跑一次 / 停止）；
  下面**结论时间线**：时间 · 档位色块 · 摘要 · 当时价 · +1h · +4h。
- **已结束**的会话也能回看（同一个弹层，时间线在下面）。
- **另一个入口**：`自动化预测 → 自动 AI` 那一格列**所有**会话（在跑的排前面，7 天内的都留着），
  每行 币种 / 进度 / 最近结论，点一行展开 +1h/+4h 和「看 K 线 / 跑一次 / 停止」。
  —— 只想"看看我盯了哪些币"时不用一个个切 K 线。
- **窄屏（≤560px，手机）** 时间线的六列会重排成一条三行：
  ① 时间 + 当时价 ② 结论（整行、最多 3 行）③ 档位 + 之后的涨跌，表头藏掉。
  —— 六列硬塞进 390px 会把「结论」挤成 `N…`，而结论正是这张表存在的理由。
  平板（≥561px）保持一行六列（`.sheet` 在 ≤900px 是全宽的，跟全站弹层一个规矩）。

## 8. 安全闸

| 闸 | 值 | 为什么 |
|---|---|---|
| 会话上限 | 8 小时（硬） | 用户定的 |
| 同时会话 | 3 个 | 多点几下别把钱包烧了（撞上限时明确提示"先去停一个"） |
| 连续失败 | 3 次 ⇒ 暂停这个会话并发通知 | 别默默一直烧 |
| 失败的一轮 | **不算** `runs` | 否则连续失败会把 32 次配额吃光 |
| 到期记录 | 保留 7 天 | 复盘用 |

**明确不做**：持久化分析**不联动下单** —— 它只负责"看"，下单还是手动 + 那套额度闸。这条边界保持住，出问题好查。
