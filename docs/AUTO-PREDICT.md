# 自动化预测（后台扫描 → 快讯式判定 → App 通知）

> 状态（2026-10-12）：**第一段「选币」已落地**（后端规则 + 网页配置 + 「筛选的币种」列表）。
> 定时扫描 / 调用模型 / 通知（FCM）还没做，见最后一节。

---

## 0. 这个功能为什么不是「让 AI 挑币」

[docs/AI-PROMPT-EXPERIMENTS.md](./AI-PROMPT-EXPERIMENTS.md) 里三批实测（≈490 次调用、
2100 次「币 × 时点」级判定）的结论：模型读结构是准的，但它的「能不能做」「谁更强」
**都没有跑赢随机**；唯一稳定跑赢的是一条零成本的傻瓜规则（按 24h 涨幅取前 5）。

所以这一套的定位是**监控 + 翻译**，不是预测机：

| 层 | 谁干 | 成本 |
|---|---|---|
| ① **选币**：从 525 个永续里挑出少数几个"值得看一眼"的 | 四条结构性规则（纯 SQL 读本地 K 线） | **0**（不碰交易所权重、不调模型） |
| ② **判定 + 人话**：把候选用一句「快讯式」说清楚 | AI（`语气 · 快讯式`） | 每次 ≈ ¥0.007~0.02 |
| ③ **通知**：只在结论值得看一眼时推 | 后端定时器 + 推送通道 | 0 |

判断它值不值得继续开着的唯一标准是**后验命中率**（通知过的"能做"，6h/24h 之后怎么样），
不是"通知有没有发出来"。⛔ 所以后面一定要把「通知时刻的价格」记下来。

## 1. 选币：漏斗

```
L0 硬性排除（SQL，免费）       525 → 约 240
L1 四条结构规则（SQL，免费）    每类各取成交额前 N
L2 合并去重 + 排序 + 配额       → 8~15 个
L3 交给 AI（快讯式）
```

**L0 排除项**（实测 525 个 TRADING 永续 → 241 个过成交额门槛 → 240 个过上市天数）：

| 排除 | 条件 | 理由 |
|---|---|---|
| 非交易中 | `symbols.status <> 'TRADING'` | 下架 / 结算中的币没有实时数据 |
| 太新 | `onboard_at` 距今 < `minAgeDays` | 没有历史结构可看 |
| 太薄 | 24h 成交额 < `minTurnover` | 滑点吃光利润 |
| 大票 | 市值排名 ≤ `excludeTopRank`（默认 30） | 用户 2026-10-12：「市值前 30 不扫」——BTC/ETH 的"放量突破"是宏观事件，不是一笔可做的单 |
| 黑名单 | `user_blacklist` 里 `until > now()` | 锁着不让开单，通知它没意义 |
| 数据不足 | 该币 K 线 < 一天根数 + 24 根 | 指标算不出来（`hi20` / `v21` 会是假的） |

⚠️ 成交额用 `sum(close × volume)` **估算**：`candles.quote_volume` 列基本是 0（实测 3 天
36750 行里只有 58 行有值），不能直接用。

## 2. 四条规则（精确判据）

变量都以**最后一根已收盘的 K 线**为"现在"，`rn` = 往前数第几根（`rn=1` 是最新那根）：

- `c0 / c3 / c_prev`：收盘价（`c_prev` 是 24 小时前那根）
- `hi20` = rn 2..21 的最高；`lo3` = rn 1..3 最低；`lo21` = rn 4..24 最低
- `v3` = rn 1..3 均量；`v21` = rn 4..24 均量；`turnover24` = Σ(rn 1..24) `close×volume`

| # | 名称 | 判据 | 抓什么 |
|---|---|---|---|
| A | 放量突破 | `c0 > hi20` 且 `v3 ≥ breakoutVol × v21` | 真突破 |
| B | 深跌转折 | `24h ≤ −dipPct%` 且 `lo3 > lo21` 且 `c0 > c3` 且 `v3 ≥ dipVol × v21` | 跌透了刚抬头 |
| C | 爆拉 | `24h ≥ rallyPct%`（**默认关**） | 已经在飞的 |
| D | 量能异动 | `v3 ≥ spikeVol × v21` 且不是 A | 有事正在发生，价还没动 |

- **判突破用收盘价，不用最高价** —— 插针不算突破（最容易误报的地方）。
- **C 默认关**：42 个「单日 +50%」的爆拉事件里 AI **全部**判"不能做"，而这些币之后 6h
  平均还摸到 +31% ⇒ 进池基本只产生"不能做"的回答 + 账单。网页上可以打开（那一格留着就是给它）。
- **一律用已收盘的那根**（`at` = 那根的 `open_time` + 一根时长），正在长的不参与 ——
  否则同一时刻重跑结果会变，后面没法复盘。

## 3. 配额与排序

**先按规则分类各取前 `perRule` 个，再合并去重、全局排序、截到 `maxPicks`。**

为什么不直接按成交额排前 12：剧烈行情里会被 D 类（量能异动）刷屏 —— 那是"吵"的一类，
不是"值得看"的一类。每类各留几个，四类才有均等的曝光机会。

类内与全局排序口径一致：**成交额降序 → 命中规则条数降序**。

~~已知取舍：按成交额排 ⇒ BTC / ETH 这类大票永远排在前面。~~ **2026-10-12 已解决**：
用户定了「市值前 30 不扫」（`excludeTopRank`，可在网页上改、0 = 不排除）。
首轮实测：243 个币里排掉 21 个（前 30 里有些本来就没过成交额门槛），
候选立刻从 BTC/ETH/SOL 变成 ENA / APT / S / ONDO / 1000PEPE / CKB / 币安人生 / ROSE。

⚠️ 这条**依赖市值排名**：排名拿不到（CoinGecko 挂了）时它不生效，
所以 `ScanResult.rankMissing` 会报出来，网页上会显示红字提示 —— 不许静默失效。

## 4. 参数（网页上配，存库）

参数**不写死在代码里**，存在 `user_scan_settings`（按用户，见 `db/scan-settings.ts`）：

| 参数 | 默认 | 说明 |
|---|---|---|
| 主周期 | `1h` | 规则里的"24h"按它换算成根数（15m→96 根 / 1h→24 根 / 4h→6 根） |
| 每类取前 | 4 | 每条规则各取成交额最大的前几名 |
| 总量上限 | 12 | 合并去重后最多几个 = 一轮最多被问几次（直接等于花费） |
| 成交额门槛 | $3M | 24h 成交额 |
| 最小上市天数 | 14 | |
| 市值前 N 不扫 | 30 | 0 = 不排除；排名拿不到时这条不生效 |
| A 量比 | 2.0 | |
| B 跌幅 / 量比 | 12% / 1.3 | |
| C 涨幅（默认关） | 20% | |
| D 量比 | 4.0 | |

**为什么存库而不是 localStorage**：扫描是**网页没开的时候**跑的，参数必须在服务端。

### 市值排名（`data/marketcap.ts`）的两个坑（2026-10-12 踩过）

1. **裸 `fetch` 不认 dotenv 加载的代理**。Node 的「环境变量代理」是**进程启动那一刻**读的
   （`NODE_USE_ENV_PROXY=1` + `HTTPS_PROXY`），而这两个变量是本项目 dotenv 在**运行时**灌进去的
   —— 对 `fetch` 来说太晚了，它永远走直连。本机直连 `api.coingecko.com` 实测 10 秒超时
   ⇒ 整套市值排名**静默失效**（用户报的「合约界面的币种市值排行怎么没了」就是这个）。
   现在这里跟 ws / ccxt 那几处一样**自己建 agent**（`https-proxy-agent`，同一个包），
   不依赖启动环境；生产没配代理 ⇒ 走直连那条分支。
2. **`https.get` 默认不发 User-Agent**，而 CoinGecko 前面那层 Cloudflare 对**空 UA 直接 403**
   （同一 URL 经代理：curl = 200、空 UA = 403）。所以必须显式带一个 UA。
3. 排名**落盘**到 `data/marketcap-ranks.json`（跟 `data/contracts.json` 一个路数）：
   免费接口会 429，只放内存的后果是"一重启就没排名 ⇒ 大票又被放回候选里"，
   而且 `npm run scan:pick` 这种短命进程每次都要重新拉。

## 5. 现在怎么用

- 网页：**开单分析 → 自动化预测**。
  - 版式（用户 2026-10-12 定，**后续新页面都照这个来**）：根节点挂 `.warm-skin`（账户统计那套暖色）、
    表格用「边框 + 圆角 + 细横线」那种；**参数收进底部弹层**（跟 K 线页那颗「配置」同一套 `.sheet`，
    **一行一项、不写说明文字**，要解释只写 `title`）。
  - 列表只有三列：**币种 / 原因 / 涨跌幅**，**点一行直接跳 K 线**看这个币
    （跟「合约行情」点一行同一个做法：`prefetchSymbol` + `pickSymbol`，窄屏再切到「K 线」那格）。
  - 右上角两颗：「重扫」（重跑这一轮）/「参数」（弹层，改完点保存会自动重扫）。
  - ★ **2026-10-15 起这一页有两格**（下面一条横向 tab）：
    「筛选的币种」（就是上面那个表）和「**AI 分析**」——
    后者列的是**所有加入过「持久化分析」的币**（在跑的排前面，7 天内的都留着），
    每行 币种 / 进度（在跑·第 N 次·还剩多久）/ 最近结论，**点一行展开**：
    那一刻往后 +1h / +4h 涨了多少 + 「看 K 线 / 跑一次 / 停止」。
    数据源就是 K 线页那个图标的同一个 store（`frontend/src/persist.ts`），进页刷一次。
    详见 [PERSIST-ANALYSIS.md](./PERSIST-ANALYSIS.md)。
- 命令行：`npm run scan:pick`（阈值默认取网页那份，env 可逐项覆盖，便于 A/B）：

```bash
TF=1h PER_RULE=4 MAX=12 TURNOVER=3000000 AGE=14 \
BREAKOUT_VOL=2 DIP_PCT=12 DIP_VOL=1.3 RALLY=1 RALLY_PCT=20 SPIKE_VOL=4 \
AT=<毫秒时间戳> npm run scan:pick
```

- 接口（都要登录）：`GET/PUT /api/scan/settings`、`GET /api/scan/picks?at=`。
  `at` 是留给回放复盘的（同一时刻重跑结果必须完全一致）。

### 这两格的分工（别搞混）

| | 筛选的币种 | AI 分析 |
|---|---|---|
| 谁在盯 | 规则扫全市场 | **你手动指定的那几个币** |
| 花钱 | 不花（纯 SQL） | 每 15 分钟（15m 会话）或每小时（1h 会话）一次模型调用 |
| 目的 | "现在有什么值得看" | "我心里那个币，AI 这 8 小时怎么说的" |

设计上的先后：先想过让"异动"自动喂 AI（见下 §6），拿 12 天真实数据回放发现**筛不出来**
（确认通过率 96%、裸用没有正期望），所以把"选币"这一步交回给人 —— **AI 分析那一格就是它的落地**。

## 6. 还没做的（按顺序）

1. **定时扫描**（`scan/scanner.ts`）：对齐 K 线收线（如每小时 `:01`）跑一轮，`at` 用
   最后一根已收盘的；同进程 `setInterval`（跟 `kline-recorder.ts` 一个路数，不用新服务）。
2. **AI 判定**：把 `runAnalysis` 从 `server.ts` 抽成独立模块并支持**指定语气**
   （固定用 `快讯式`，不跟着用户当前勾选的那份变）；候选的 `ruleLabels` 要写进上下文
   （否则模型不知道自己为什么在看这个币）。
3. **`alerts` 表 + 去重**：同一 `币种+周期` 冷却 6h、结论翻转才推、"能做"才推、
   静默时段（00:30–07:30）、每轮最多 1~3 条。
4. **通知通道**：用户 2026-10-12 选的是 **FCM 真推送**（App 被杀也能收到）——
   需要 Firebase 项目 + `google-services.json` + `@capacitor/push-notifications` +
   服务端用服务账号发 HTTP v1 + 重打 APK；同时做站内铃铛（SSE，复用现有那套）。
5. **复盘页**：通知后 6h/24h 的后验 + 每类规则的命中率（决定阈值往哪调、这功能要不要继续开）。
6. **成本硬闸**：日花费上限（到了就跳过并记一条）+ 连续失败熔断 + 单轮并发上限。
